# 3-D Secure

3-D Secure (3DS) lets the card issuer confirm that the person paying is the legitimate cardholder. For cards issued in the European Economic Area, strong customer authentication is a regulatory requirement for most online payments, and 3DS is how it is performed. Qorvex Pay supports EMV 3-D Secure version 2.2 for Visa and Mastercard.

## Frictionless and challenge flows

When you create a payment, Qorvex Pay sends the transaction data and the information you supplied about the customer to the issuer's Access Control Server (ACS). The issuer then chooses one of two flows:

| Flow | What the customer sees | What happens in the API |
|---|---|---|
| Frictionless | Nothing; authentication happens in the background | The payment is authorized or declined in the create request |
| Challenge | A page from their bank asking for a one-time code, a banking app confirmation or biometrics | The payment waits in status `awaiting_3ds` until the customer completes the challenge |

The issuer decides which flow to use. You can increase the share of frictionless authentications by sending `customer.email` and `customer.ip` with every payment: the more data the issuer has, the more often it can approve without a challenge.

## Authentication mode

The `authentication.mode` parameter of `POST /v2/payments` controls when 3DS is attempted.

| Value | Behaviour |
|---|---|
| `auto` | Default. Qorvex Pay attempts 3DS whenever regulation requires it or the risk engine recommends it. Exemptions are requested automatically where they apply. |
| `force` | 3DS is attempted for every payment, regardless of regulation and risk score. Useful for high-risk goods or if your account has an elevated fraud rate. |

There is no value that turns 3DS off. When the issuer does not participate in 3DS, or the card is issued outside the regions where authentication is mandatory, the payment continues without authentication and `authentication.status` reflects that.

## Challenge flow step by step

1. **Create the payment** with a `return_url`. The URL must use HTTPS and should point to a page on your site that can look up the order.
2. **Check the status.** If the response has `status: awaiting_3ds`, the payment needs a challenge. The `authentication.challenge_url` field contains the URL of the challenge page.
3. **Send the customer to the challenge.** Redirect the customer's browser to `challenge_url` with a full-page redirect. The challenge page is served by Qorvex Pay and embeds the issuer's ACS.
4. **The customer authenticates** with their bank.
5. **The customer returns** to your `return_url`. Qorvex Pay appends the ID of the payment as the `payment_id` query parameter, so your return page knows which payment to look up.
6. **Confirm the result on your server** by retrieving the payment. The status is now `authorized` (or `captured` for `capture_mode: auto`) if authentication succeeded, or `declined` if it failed.

Never treat the redirect itself as proof of payment. Customers can close the tab, lose connectivity or open the return URL manually. Always confirm the status with `GET /v2/payments/{id}` or with the webhook that announces the result.

## Challenge session lifetime

A challenge session lasts 20 minutes from the moment the payment enters `awaiting_3ds`. If the customer does not complete the challenge within 20 minutes, the session ends, the payment moves to `declined`, and the `decline_code` field explains that authentication was not completed in time. The exact code is listed among the decline codes in the Errors section.

After the session has ended, the challenge URL shows an expiry page and redirects the customer to your `return_url`. To let the customer try again, create a new payment.

Do not keep customers waiting on your side for the full session lifetime: if your checkout shows a spinner while the customer is at the bank, offer a link back to the cart after a few minutes.

## The authentication object

The payment object contains an `authentication` object when 3DS was attempted, and `null` otherwise.

| Field | Type | Description |
|---|---|---|
| `status` | string | `frictionless`, `challenge_required`, `succeeded` or `failed` |
| `challenge_url` | string or null | URL of the challenge page while `status` is `challenge_required`; `null` otherwise |
| `eci` | string or null | Electronic Commerce Indicator returned by the scheme |
| `liability_shift` | boolean | Whether liability for fraud-related losses has moved to the issuer |
| `version` | string | 3DS protocol version used, for example `2.2.0` |

### Authentication status values

| Status | Meaning |
|---|---|
| `frictionless` | The issuer authenticated the cardholder without a challenge |
| `challenge_required` | The cardholder must complete a challenge; the payment is in `awaiting_3ds` |
| `succeeded` | The cardholder completed the challenge successfully |
| `failed` | Authentication failed or was rejected by the issuer; the payment is declined |

## Retrieve authentication details

`GET /v2/payments/{id}/authentication`

Returns the authentication object together with additional technical details that are useful for support cases, such as the directory server transaction ID and the time the challenge was completed.

```json
{
  "payment_id": "pmt_01JC9C7R2T4V6X8Z0B1D3F5H7K",
  "status": "succeeded",
  "eci": "05",
  "liability_shift": true,
  "version": "2.2.0",
  "ds_transaction_id": "f38e6948-5388-41a6-bca4-b49723c19437",
  "challenge_completed_at": "2026-10-14T10:04:52Z"
}
```

## ECI values

The Electronic Commerce Indicator summarises the outcome of authentication. Values differ between schemes:

| Scheme | ECI | Meaning |
|---|---|---|
| Visa | `05` | Fully authenticated |
| Visa | `06` | Authentication attempted; issuer or cardholder not enrolled |
| Visa | `07` | Not authenticated |
| Mastercard | `02` | Fully authenticated |
| Mastercard | `01` | Authentication attempted |
| Mastercard | `00` | Not authenticated |

## Liability shift

When a payment is fully authenticated, the scheme rules usually move the liability for fraud-related losses from you to the issuer. The `liability_shift` field tells you whether this happened for a particular payment. It is `true` for fully authenticated payments and, depending on scheme rules, for some attempted authentications.

Liability shift is not a guarantee of payment. It applies only to fraud-related losses where the cardholder's identity is in question.

## Testing 3-D Secure in the sandbox

The sandbox includes a simulated ACS so you can test every branch of the flow without a real bank. Use the test cards from the Testing section: one card always authenticates without a challenge, one always asks for a challenge, and one always fails authentication.

When you use the challenge card, the simulated ACS page asks for a one-time code. Enter `0610` to complete the challenge successfully. Any other code fails authentication, and the payment is declined. You can also leave the page open to test what happens when the challenge session expires.

## Implementation checklist

- Always send `return_url`, even if most of your customers authenticate without a challenge.
- Redirect to `challenge_url` with a full-page redirect.
- Confirm the result on the server; never rely on the redirect alone.
- Handle both outcomes on the return page: success and failure.
- Send `customer.email` and `customer.ip` to improve frictionless rates.
- Listen to payment webhooks so that orders are updated even when the customer does not come back to your site.
